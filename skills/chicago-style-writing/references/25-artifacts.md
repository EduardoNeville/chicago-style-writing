# Text that lives in another artifact

Most text an agent produces is not a document. It is a JSON script read aloud by
speech synthesis, a component string shipped to a browser, a translation entry, a
title card in a rendered video. The words are consumed by something expensive, and
after that they are hard to change.

The skill still applies. The job is to make the words visible as prose before
anything consumes them.

## Three laws

1. **Lint the source of truth, never generated output.** Built HTML, bundled JS,
   rendered frames, and generated manifests are artifacts. The file a human edits is
   the source. A finding in a build artifact is noise; a finding in the source is a
   fix.
2. **Words live in one declared file per register, before layout.** If they are
   scattered through markup, extract them once and let the code read from the
   extraction. Text that lives only inside a template cannot be linted, and it
   drifts from the design that was approved.
3. **Freeze the words before the artifact consumes them.** Record a hash of the text
   when audio, screenshots, or a render are produced. If the text changed afterwards,
   the gate fails: the artifact is stale.

## Registers

A register names who reads the text and through what. It selects which mechanical
rule families apply. It never switches off a slop rule.

| Register | What it is | Examples | Switched off |
| `prose` (default) | running text | essays, docs, README, reports | nothing |
| `spoken` | read aloud | narration, podcast and video scripts | apostrophe direction, prose hints |
| `display` | on screen, not a sentence | titles, kickers, footers, cards, chart labels | sentence structure, colon-after-verb, sentence-initial numeral |
| `ui` | frontend strings | buttons, errors, empty states, tooltips | abbreviation, numeral, range, ellipsis, quote form |

The same fact takes opposite forms inside one artifact. A video's narration says
"thirty forecasts of a single question"; the footer on the same scene reads `Table 1
· at 25 cruxes per side`. Words in one register, numerals in the other, and both
correct.

A label is not a sentence, so a fragment is not present and nothing is flagged.
`display` copy that does contain a fragment stack, a binary contrast, or a colon
reveal is an error like anywhere else.

## The inventory contract

One entry per line, `id` + TAB + text, so every finding maps back to a beat, a
component, or a key:

```
b07	The forecast it wrote leaned on something else.
b08	The multiple-rollout method adds a third.
```

- Path: `text/<register>.md`, inside the artifact's project.
- Generated by the project, committed, reviewed in the diff like any other file that
  is generated but meaningful (`cues.txt`, `timeline.json`).
- Quoted matter gets a leading `>` so the rule exemptions apply (2.67).
- The skill ships no extractor. Only the project knows where its words live.

Extracting JSON is one line:

```bash
jq -r '.[] | "\(.id)\t\(.text)"' script.json > text/narration.md
```

Extracting visible strings from markup means stripping tags and keeping text nodes.
If that is more than a short script, the better fix is to move the copy into a data
file and have the markup read it, which is law 2 anyway.

## Gate wiring

Put the gate before the expensive step, not after the artifact exists.

```
text gate  ->  synthesis  ->  build  ->  render  ->  publish
```

- **Before synthesis or render**: lint each inventory with its register. Both must
  be clean (`--errors-only`).
- **At the same place as the project's existing checks**: one line in the project's
  `AGENTS.md` or `CLAUDE.md` beside the command the agent already runs after every
  edit.
- **Freeze**: write the hash when synthesis runs; fail the gate if the text changed
  after it.

```bash
python3 path/to/scripts/cmos_lint.py --register spoken  text/narration.md
python3 path/to/scripts/cmos_lint.py --register display text/onscreen.md
```

## Worked example: a video essay

A nine-minute narrated explainer built from `script.json` (one entry per beat),
scene files that carry `kicker`, `foot_l`, and `foot_r` strings, a build step that
turns word indices into reveal timings, and a render.

Words become audio (a quota-limited speech service), then word-level alignment, then
reveal timing, then a five-minute render. A text change after that costs a synthesis
request, a realign, a rebuild, a structural check, fresh frame snapshots, and a
re-render. The same change before synthesis costs nothing.

What the gate found in text that had already been reviewed by eye:

- 8 errors on the extracted narration were straight apostrophes in a register read
  aloud, where the mark is inaudible and correct in source. The `spoken` register
  removed all eight.
- The narration held one true slop pattern: `make a decision` instead of `decide`
  (`SLOP.WEAK_VERB`).
- Display chrome produced four meaningless hints ("sentence is 139 words long") from
  a splitter that had no sentence to split. The `display` register removed them.
- Zero em dashes had been used, because the project had already chosen `·` as its
  separator. A house rule that costs nothing is worth having in writing anyway.

The style sheet that project implies but never wrote down, and which the gate now
enforces: kickers in title case, footers in sentence case, `·` as separator, no
terminal punctuation on screen, numerals spelled out in narration.

## What this does not cover

- No HTML, JSX, Python, or template parser in this skill. Extraction is the project's
  job, because only the project knows which strings a reader sees.
- No linting of built output, rendered frames, captions, or OCR.
- Voice-over pronunciation, timing, and loudness are not prose problems.
